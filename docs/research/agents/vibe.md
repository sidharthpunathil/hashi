## Notes

Read from `~/.opensrc/repos/github.com/mistralai/mistral-vibe/main` (pyproject 3.1.2, CHANGELOG 2026-11-10). Not executed; fixtures derived from source. **Architecture changed:** the `vibe` console script (`vibe/cli/launcher.py:43-74`) now execs a Rust client `vibe-rs` (clap, `vibe/cli-rust/src`), which spawns a Python `vibe-app-server` subprocess and talks JSON-RPC to it. On SIGKILL the app-server follows (immediately on Linux, within about a second on macOS: docs/programmatic-mode.md:84-88), which matters for Hashi's `kill_on_drop`.

**Headless.** `-p/--prompt [TEXT]` or `--prompt-file PATH` (`cli-rust/src/cli.rs:62-64, 104-110, 433-436`). The positional `[initial_prompt]` is for the TUI only and is ignored in headless mode (`cli.rs:58-60, 449-466`), so `-p -- <text>` would run with an EMPTY prompt read from stdin and fail with `No prompt provided for programmatic mode`. Use `--prompt=<text>` (clap attached value; works for text starting with `-`). With text given, stdin is never read (`cli.rs:438-446`). Untrusted workspace: project `.vibe/` config is ignored with a stderr warning, not an error (`headless_trust.rs:18-39`); do not pass `--trust`.

**Output** `--output text|json|streaming` (`cli.rs:17-28, 66-73`, `headless_output.rs`):
- `text`: only the final assistant text (last assistant message of this turn, text blocks joined by blank lines, `headless_output.rs:93-99, 149-162`). No session id.
- `json`: one pretty-printed JSON ARRAY of the whole session history at the end (`headless_output.rs:88-91`); on resume it includes earlier runs.
- `streaming` (chosen): one compact JSON object per history entry, written when the entry's `generationStatus` becomes `completed` (`headless_output.rs:34-80, 110-112`). Entries are app-server `PublicHistoryEntry` objects, camelCase via `ProtocolModel` (`vibe/app_server/_model.py:9-16`): base `{id, sessionId, turnId, inputEntryId, createdAt, updatedAt, generationStatus, relatedEntryId}` (`vibe/app_server/models.py:866-874`) plus `type` = `message` {role: system|user|assistant, content:[{type:"text",text}|{type:"image",...}], source, userDisplayContent, outcome{type: committed|discarded, cause?}} (models.py:898-919), `reasoning` {text, summary, outcome}, `effect` {title, detail{toolName,...}, state{error{code,message}, approvalSource}} (tool calls), `callback`, `checkpoint`, `notice`.
- Parser caveats Hashi's generic jsonl mode cannot express: (1) the user's own prompt is also a `type:"message"` entry (role user), so the reader should take the last `message` with `role == "assistant"`, skip `outcome.cause == "retry"`, and join every `content[].text` block, mirroring `last_assistant_text` (`headless_output.rs:151-162`); `/content/0/text` with `last` only works for single-block answers. (2) `sessionId` is on every entry, good.
- **No usage or cost on stdout in any format.** Tokens, `cost_usd`, `steps`, `session_id`, outcome and warnings are only in `DIR/export.json` written with `--output-dir DIR` (docs/programmatic-mode.md:57). Hashi could pass `--output-dir <scratch>` and read that file, which the current stdout-only parse contract cannot do.
- **Failure:** nothing distinctive on stdout (entries produced so far, possibly none); stderr gets `Error: <message>` or `Stopped: <outcome>` (`headless.rs:75-83`, `headless_run.rs:167-168`); text mode with no answer prints `The agent finished without an answer.` on stderr. Hence `fixture_error: null`.
- Exit codes (docs/programmatic-mode.md:74-82): 0 finished; 1 usage_error/config_error; 2 infrastructure_failure (model API after retries, runtime); 3 turn_limit/token_limit/price_limit/deadline/terminated/length/refusal; 4 aborted (agent socket).

**Resume.** `--resume <SESSION_ID>`; a bare `--resume` is a usage error headless (`cli.rs:613`, message `--resume requires a session ID in programmatic mode`). `-c/--continue` resumes this terminal/folder's last session. Session ids cannot be pre-assigned; format looks like a UUID (UNVERIFIED, read it from `sessionId`). **`--model` together with `--resume`/`-c` is a usage error: `--model only applies to a new session`** (`cli.rs:531`), so Hashi must drop the model flag on resume.

**Model.** `--model ALIAS` is a configured model alias (for example `devstral-2`), applied to this session only (`headless/config.rs:35-48`); an unknown alias is a usage error.

**Permissions.** Headless never prompts: a tool call that would ask is denied and the model is told; each denial is reported on stderr as `Tool call denied: <tool> (needs approval, which a headless run cannot give)` (`headless_output.rs:126-147`, docs/programmatic-mode.md:17-32). The default agent is the user's `default_agent`, normally `accept-edits`, which auto-approves `write_file` and `edit` (`vibe/core/agents/models.py:92-103`). Pinning `--agent ask` ("Requires approval for tool executions", models.py:87-91) means only tools whose own permission is `always` run (read/grep style tools; exact per-tool defaults UNVERIFIED), so bash and writes are denied. `ask_user_question` and `cron` are always disabled headless (`headless/config.rs:50-60`). Unsafe: `--auto-approve`/`--yolo` (bypass all permissions, `AUTO_APPROVE` profile models.py:104-110), `--smart-approve` (model classifier decides), `--trust` (loads project `.vibe/` config, hooks, MCP and tools from the workspace), `--agent auto-approve` (Hashi should refuse an operator `--agent` override of the pinned value; UNVERIFIED whether `--agent` is honoured on `--resume`, docs say a resumed session keeps its agent). `--enabled-tools` disables all other tools in programmatic mode (docs/programmatic-mode.md:46), which is a useful extra lock (for example `--enabled-tools read_file --enabled-tools grep`) but tool names were not fully verified, so it is not pinned.

**Slash.** A prompt whose first token is `/name` invokes the skill `name`, and `/name` mentions elsewhere outside code also load skills (`vibe/app_server/_skill_invocation.py:41-70`).

**Env and config.** `VIBE_HOME` relocates `~/.vibe` (config.toml, `.env` with saved keys, session logs, trusted folders, agents, skills: `vibe/utils/vibe_home.py:10-13`, `vibe/core/paths/_vibe_home.py:16-20`). API keys saved in the OS keyring are NOT relocated by `VIBE_HOME`; headless prints `Reading API keys from the <keyring> ...` on stderr unless `MISTRAL_API_KEY` is set (`cli-rust/src/headless_startup.rs:18-33`); the only switch is the test var `VIBE_TEST_DISABLE_KEYRING=1` (`credentials/keyring.rs:6, 17-19`). Any config key can be overridden with a `VIBE_` env var (pydantic-settings `env_prefix="VIBE_"`, `vibe/core/config/layers/environment.py:17`), e.g. `VIBE_ACTIVE_MODEL`, `VIBE_PROVIDERS`; providers name their own `api_key_env_var` (default `MISTRAL_API_KEY`, `vibe/core/config/_defaults.py:9`). `VIBE_CWD` equals `--workdir`. Commands the agent runs get `VIBE_SESSION=1`. Update checks and telemetry in headless mode: UNVERIFIED (an `update` command and `--check-upgrade` exist).

**Rate limits.** The harness classifies HTTP 429 as retry category `rate_limited` and labels errors `HTTP <status>` with the provider's `error.message` (`harness/runtimes/python/python/mistralai_vibe_local_harness/vibe/adapters/_provider_failure.py:44-45, 186, 257-260`); 429 is retried, then the run ends `infrastructure_failure`, exit 2, with `Error: ...` on stderr. Exact Mistral 429 wording UNVERIFIED ("capacity exceeded" is a guess). Budget stops (`--max-tokens`, `--max-price`) end with exit 3 and `Stopped: token_limit|price_limit`.

## Hashi features (coverage pass, 2026-11-16)

- **Login accounts:** yes. Every stored login is an API key named by the provider's env var (MISTRAL_API_KEY). persist_api_key writes it to the OS keyring first (service ai.mistral.vibe, account = env var name, shared by every VIBE_HOME) and only falls back to $VIBE_HOME/.env when the keyring write fails (vibe/setup/auth/api_key_persistence.py:224-258, vibe/utils/keyring.py:15-17,314-326). So VIBE_HOME alone is not enough: a second sign-in would overwrite the owner's keyring key. VIBE_TEST_DISABLE_KEYRING=1 is honoured in production code by both the Python app-server (keyring.py:44-45,315-317) and the Rust client (vibe/cli-rust/src/credentials/keyring.rs:6,17-19), which forces the .env fallback. At run time $VIBE_HOME/.env is loaded into the environment before any keyring read (vibe/core/config/vibe_schema.py:176-197, vibe/app_server/stdio.py:211, vibe/cli-rust/src/credentials/dotenv.rs:17-40) and the environment wins over the keyring (vibe/utils/api_keys.py:75-89,101-124), so the account key is used even if the keyring also has one. Hashi should put VIBE_TEST_DISABLE_KEYRING=1 in account_env (sign-in and runs) and set dir_var VIBE_HOME.
- **API-key accounts:** yes. Resolution order is session credential, then a non-empty process env value, then the keyring (vibe/utils/api_keys.py:101-124; Rust mirror vibe/cli-rust/src/credentials/mod.rs:13-26); $VIBE_HOME/.env never overrides an explicit env value (vibe_schema.py:191-193, dotenv.rs:29-35). The one exception is VIBE_CLI_OIDC_ENABLED=1, which makes MISTRAL_API_KEY resolve only from the OIDC session and ignore the env key (api_keys.py:92-98,110-114; credentials/mod.rs:14-17); that var is already in credential_vars, so Hashi strips it. Caveat: the owner's config.toml active_model/providers (or VIBE_ACTIVE_MODEL) can still pick a non-Mistral provider whose key comes from another env var.
- **Status check:** {"args": null, "signed_in_when": null}
- **Identity:** {"file": null, "pointer": null, "jwt_claim": null}
- **Switch:** yes. With the keyring off an account's login is one plain file, $VIBE_HOME/.env (vibe/core/paths/_vibe_home.py:17, VIBE_HOME default ~/.vibe at vibe/utils/vibe_home.py:7-13). Copying it into ~/.vibe/.env switches the plain `vibe` command even when the owner's original key sits in the keyring, because .env is injected into the environment and env beats keyring (vibe_schema.py:176-197, api_keys.py:84-89). Switching back to default restores the original .env (often absent), and the keyring key takes over again. Caveats: (1) the owner's own login is normally in the keyring, not in .env, so Hashi sees default as 'no file' (its absent-original path); (2) .env is the whole dotenv file, so other saved values (proxy settings written by vibe/core/proxy_setup.py, other provider keys) move with it; (3) if the owner reruns `vibe --setup` while switched, the new key goes to the keyring and MISTRAL_API_KEY is deleted from ~/.vibe/.env (api_key_persistence.py:250-258), silently undoing the switch. API keys carry no expiry. OIDC logins (VIBE_CLI_OIDC_ENABLED) are keyring-only and cannot be switched.
- **Live quota:** yes. vibe/app_server/_billing.py:1-8,27-53,72-92 reads both paths relative to the provider api_base (DEFAULT_MISTRAL_API_BASE, vibe/core/config/_defaults.py:13); the app shows it as AccountBudgetView (vibe/app_server/models.py:120-126). /budget needs the see_org_inference_usage permission and answers 403 otherwise, and self-hosted platforms may 404 (_billing.py:5-7,107-110), so treat failures as unknown. /whoami: vibe/setup/auth/whoami.py:39-40,60-93 (plan only, no remaining amount).
- **Usage in output:** none
- **Limit messages:** Headless prints failures on stderr as `Error: <message>` or `Stopped: <outcome>` (vibe/cli-rust/src/headless.rs:75-80, headless_run.rs:168,196). HTTP 429 is retried with category `rate_limited` and label `HTTP 429` (harness/.../vibe/adapters/_provider_failure.py:44,186,257-260), then the turn fails with code `rate_limit` (vibe/app_server/_unified_harness_backend_adapter.py:15800-15806); the message is the provider text, which for Mistral is typically 'Requests rate limit exceeded' or 'Service tier capacity exceeded for this model' (provider wording not in source), both matched by 'rate limit' / 'capacity exceeded'. The friendly 'Rate limits exceeded. Please wait a moment...' text is TUI-only (event_handler.rs:984-994) but is also matched by 'rate limit'. 'http 429' and 'rate_limited' may never reach the user-visible message (label and category are separate fields); harmless. Budget stops (--max-tokens/--max-price) end `Stopped: token_limit|price_limit` with exit 3; these are run caps, not account limits, so leaving them out is right. Missing candidate: none found for an exhausted monthly Vibe allowance (no distinct message in source; payg_enabled means usage past 100% is billed instead of paused, models.py:124-125).
