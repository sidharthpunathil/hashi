# Security model

Anyone holding a token can make your agent run on your computer with your account, so Hashi starts locked down. To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## What a token can and cannot do

- **Tokens.** Each token is 256 bits from the OS random generator, prefixed `hashi_` so secret scanners recognise it. The database stores only its SHA-256 hash.
- **Least privilege.** Tokens default to the `user` role. Only admins manage tokens, and the last admin cannot be revoked. Requests are visible only to the token that made them, and to admins.
- **No shell.** Agents are started directly with an argument vector. The prompt always follows `--`, so it can never be read as a flag. Model names and session ids are checked against a strict alphabet and may not start with `-`. Prompts starting with `/` get a leading space, so a shared user cannot reach commands like `/config` in Claude Code, Gemini CLI or Qwen Code.
- **Sandboxed by default.** Each agent runs headless with its safest unattended setting (see the [agent table](../README.md#supported-agents)). Loosen Claude Code and Codex deliberately with `--claude-permission-mode` and `--codex-sandbox`. The other defaults cannot be changed from Hashi in this release.
- **Agents run as you.** An agent run uses your account and can read whatever your account can, unless the agent's own sandbox stops it. That includes `~/.hashi/hashi.db` (every token's prompts and answers) and other tokens' workspaces; only opencode is confined to its workspace. Share agents that can read files only with people you would trust with them. Hashi removes its own settings (`HASHI_*` variables and `TUNNEL_TOKEN`) from every agent's environment, so a run never sees your tunnel token.
- **Isolated workspaces.** Every token gets its own working directory for each agent, under `~/.hashi/workspaces/<token>/<agent>/`. One agent with write access can never plant project config (such as hook definitions in `.claude/settings.json` or `.gemini/settings.json`) that a different agent would load.
- **Accounts.** A run on an account other than `default` first removes that agent's credential variables inherited from you, then sets the account's own directory or key, so an `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` in your shell cannot outrank the account. Besides keys and tokens this removes everything that would send the run to another provider, endpoint or cloud account of yours (a `*` is a prefix):
  - Claude Code: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_CUSTOM_HEADERS`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`, `CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR`, `CLAUDE_CONFIG_DIR`, the provider switches `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY` with their `CLAUDE_CODE_SKIP_*_AUTH` forms, `ANTHROPIC_BEDROCK_*`, `ANTHROPIC_VERTEX_*`, `ANTHROPIC_FOUNDRY_*` (such as `ANTHROPIC_FOUNDRY_API_KEY` and `ANTHROPIC_VERTEX_PROJECT_ID`), `AWS_*` (`AWS_BEARER_TOKEN_BEDROCK`, the AWS keys, profile and region), `GOOGLE_CLOUD_*`, `GOOGLE_APPLICATION_CREDENTIALS`, `GCLOUD_PROJECT`, `CLOUD_ML_REGION` and `VERTEX_REGION_*`.
  - Codex: `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `CODEX_HOME`, `CODEX_SQLITE_HOME`, `OPENAI_BASE_URL`, `OPENAI_ORGANIZATION`, `OPENAI_ORG_ID`, `OPENAI_PROJECT`, the workload identity variables (`OPENAI_IDENTITY_TOKEN_FILE`, `OPENAI_WORKLOAD_IDENTITY_CONTEXT`, `OPENAI_FEDERATION_RULE_ID`), `CODEX_AUTHAPI_BASE_URL`, `CODEX_REFRESH_TOKEN_URL_OVERRIDE` and `CODEX_APP_SERVER_MANAGED_CONFIG_PATH`.
  - Gemini CLI: `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GENAI_USE_GCA`, `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_CLOUD_*` (`GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION`), `GOOGLE_GEMINI_BASE_URL`, `GOOGLE_VERTEX_BASE_URL`, `GEMINI_CLI_HOME`, `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE`, `GEMINI_CLI_USE_COMPUTE_ADC`, `GEMINI_DEFAULT_AUTH_TYPE`, `GEMINI_CLI_AUTH_OVERRIDE`, `GEMINI_CLI_TRUST_WORKSPACE`, `GEMINI_CLI_TRUSTED_FOLDERS_PATH`, `GEMINI_CLI_SYSTEM_SETTINGS_PATH`, `GEMINI_CLI_SYSTEM_DEFAULTS_PATH`, `GEMINI_CLI_IDE_*` and `CLOUD_SHELL`.
  - Qwen Code: `QWEN_HOME`, `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_CLOUD_*` and the key variable of every provider preset it ships (`DASHSCOPE_API_KEY`, `BAILIAN_CODING_PLAN_API_KEY`, `BAILIAN_TOKEN_PLAN_API_KEY`, `QWENCLOUD_API_KEY`, `QWENCLOUD_TOKEN_PLAN_API_KEY`, `DEEPSEEK_API_KEY`, `IDEALAB_API_KEY`, `ZAI_API_KEY`, `REQUESTY_API_KEY`, `MODELSCOPE_API_KEY`, `MOONSHOT_API_KEY`, `MINIMAX_API_KEY`, `XAI_API_KEY`, `OPENROUTER_API_KEY`, `OPENCODE_GO_API_KEY`).
  - Cursor CLI `CURSOR_API_KEY`; opencode `XDG_DATA_HOME`, `OPENCODE_DB`; Crush the provider variables in its README (see [Crush](#crush)).

  Runs on `default` keep your environment as it is, apart from Crush's.
- **Key accounts have their own config too.** A key account's run also points the agent's directory variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GEMINI_CLI_HOME`) at the account's own `0700` directory, the one holding its key file. Without that the agent would load your own `~/.claude` settings (whose `apiKeyHelper` or `env` can supply another key), `~/.codex` config or `~/.gemini` settings (whose `security.auth.selectedType`, such as `oauth-personal`, outranks `GEMINI_API_KEY`), and the run could use your login instead of the key. A Gemini key account's `settings.json` selects `gemini-api-key`. Cursor CLI has no directory variable, so its key accounts still load your Cursor config.
- **Gemini CLI `.env` files.** Gemini CLI walks up from the working directory to the filesystem root and loads the first `.env` it finds, falling back to `<home>/.env` (`findEnvFile`, `packages/cli/src/config/settings.ts:607-643` in gemini-cli 0.69.0-nightly). For a workspace under your home, that is your own `~/.env`, and in an untrusted folder it still loads `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_CLOUD_PROJECT` and `GOOGLE_CLOUD_LOCATION` from it (`settings.ts:91-96`). No environment variable turns this off; the setting `advanced.ignoreLocalEnv` (`settingsSchema.ts:2059`) does, after which only a `.env` directly in `GEMINI_CLI_HOME` loads (`settings.ts:623`, with `homedir()` from `packages/core/src/utils/paths.ts:22-28`). Every non-default Gemini account therefore has `GEMINI_CLI_HOME` set to its own directory and `advanced.ignoreLocalEnv: true` written into its `settings.json`, keeping anything else the CLI wrote there; a run is refused when that file is not plain JSON Hashi can update. The `.gemini/.env` files on the same walk load only in a trusted folder, and a Hashi workspace is not trusted when settings load (`--skip-trust` takes effect afterwards, `config.ts:527-529`; `GEMINI_CLI_TRUST_WORKSPACE` is removed). The `default` account keeps Gemini CLI's own behaviour. Account directories are `0700` and key files `0600`; a key is read from a variable or from standard input without echo, never from the command line, and is never logged, put in `hashi report` or returned by the API. Hashi never reads, copies or refreshes an agent's login. Token holders never see account names, and an account's directory or key is replaced by `<account>` in errors they get.

## Crush

Crush is opt-in (`--enable-crush`) because its headless mode has no approval step: `crush run` approves every permission request of its own session (`internal/app/app.go:447-449` in the Crush source), so `-y` and `--yolo` change nothing and are never passed. What Hashi does instead:

- **Tools.** Before every run Hashi writes `<data-dir>/crush.json`, the workspace config Crush merges after every other file, with `options.disabled_tools` listing every tool that can write, run code, reach the network or start a sub-agent: `bash`, `job_output`, `job_kill`, `download`, `edit`, `multiedit`, `write`, `lsp_rename`, `lsp_replace_symbol`, `lsp_restart`, `fetch`, `agentic_fetch`, `sourcegraph`, `agent`, `agent_dispatch`, `agent_send`, `agent_status`, `agent_stop`, `crush_info`, `crush_logs`, `list_mcp_resources`, `read_mcp_resource` and `question`. It also sets `auto_lsp: false` and `disable_metrics: true`. What is left is `view`, `ls`, `glob`, `grep`, `todos` and the read-only LSP queries.
- **Tool gate.** Crush has no command that lists its tools, so Hashi checks the version instead: `crush --version` must report 0.100.x, the release whose tool list Hashi was checked against. A newer release could add a tool that is neither allowed nor denied, and Crush would run it without asking, so it is refused unless you pass `--crush-allow-newer`. So is any pre-release or build with a suffix (`v0.100.1-0.20261105...`, `v0.100.0-devel+dirty`), which may carry tools no release has. An older release, or a version Hashi cannot read, is refused too.
- **Project config.** Crush loads `.crushrc`, `crushrc`, `.crush.json` and `crush.json` from the working directory up to the repository root, and runs a crushrc as shell code. Hashi refuses the run when any of them is in the workspace or any parent up to the filesystem root, past the repository root too, so the check holds whatever Crush's own walk does. The check runs before the version probe and again under the data directory's lock right before each spawn, so a config planted in between (by the probe, or by another run in the same workspace) never loads. It also refuses a workspace with a `.env`, which Crush loads into its own environment, and any run while `/etc/crush/crush.json` exists, since that file can add MCP servers and hooks Hashi cannot turn off.
- **Your config never loads.** Every Crush account, `default` included, has its own directory under `~/.hashi/accounts/crush/`, and each run points `CRUSH_GLOBAL_CONFIG`, `CRUSH_GLOBAL_DATA`, `CRUSH_CACHE_DIR`, `CRUSH_SKILLS_DIR` and `HOME` into it, so `~/.config/crush` with its MCP servers and hooks stays out. Every inherited `CRUSH_*` variable (each stands in for the variable of the same name without the prefix) and `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME` and `XDG_STATE_HOME` are removed from every run. Runs on other accounts also lose the provider variables listed in Crush's README. `CRUSH_DISABLE_METRICS`, `DO_NOT_TRACK` and `CRUSH_DISABLE_PROVIDER_AUTO_UPDATE` are set.
- **Sessions.** `crush run` prints no session id, so Hashi asks `crush session last --json` afterwards. Runs in the same data directory (one per account and workspace) are serialised inside Hashi so that answer is the right session. Two Hashi processes running Crush at once are not serialised.

What this does not cover: the read tools ask before reading outside the workspace, and the run approves that too, so Crush can read any file your user can read. Crush also checks GitHub for a newer release on every start, and nothing turns that off.

## Protecting your machine

People you share with decide when agents start, so Hashi keeps your computer usable whatever a token does.

- Runs across all agents are capped (`--max-running`, from your memory and CPU count).
- Before a run starts, Hashi checks that it would still leave your memory reserve free and that the disk under `~/.hashi` is above its floor. If not, the request waits in the queue, keeping its place, and the dashboard shows "held: low memory" or "held: disk".
- While a run is active, its whole process tree (the agent plus every shell or server it spawns) is measured every 2 seconds and stopped above `--run-memory-limit`, failing that request with the measured and allowed sizes.
- Each run gets its own process group on Unix and a Job Object on Windows, so a timeout, memory stop, output overflow or shutdown kills everything it started. Agents run at a lower priority (`--nice 10`).
- Processes that detach into their own session are tracked too: their memory counts against the run, and they are killed when it ends. On Linux Hashi adopts orphaned descendants so none can slip away; on macOS one that detaches and loses its parent between two samples can still escape.
- Memory and disk figures appear only in the dashboard and the admin `GET /v1/stats`, never on `/v1/status`, `/v1/me` or MCP.

## Fair sharing and limits

- Bodies over 64 KB and prompts over 32 KB are refused, and a request body must arrive within 10 seconds. One client address may hold at most an eighth of the connection slots (at least 4; loopback, where tunnels and proxies connect from, is exempt).
- Each run is killed after its timeout (default 5 minutes) or once it prints more than 10 MB. There is a per-token rate limit (default 60 requests per minute) and a global queue cap.
- A `user` token created without limits may have 3 prompts in flight; invite tokens get the same default and admins stay unlimited. In-flight, queue, request and spend caps are checked in the same database transaction as the insert, so a burst of parallel requests cannot slip past them.
- The last 10% of the queue (at least 5 slots, at most half) is kept for admin tokens, so a flood from people you share with never locks you out.
- Each token may hold at most 4 long polls open at once; a further wait answers at once with the current state (202).
- Invalid tokens and invite codes are rate limited per client address, but a valid token or code always works, so someone guessing from your address cannot lock you out.

## Projects

A project only changes where a run starts. It does not change what an agent running as you can read: an agent in a project folder can still read whatever your user can, as it could from its private workspace. Share only folders you trust the people you share with to see, and whose contents you trust.

- Hashi never creates, changes, moves or deletes anything in a project folder. Revoking a token deletes only its own workspace under `~/.hashi/workspaces/`, removing a project deletes only Hashi's record of it, and `hashi uninstall` leaves project folders alone: a project path cannot be inside the Hashi home, so deleting the home cannot reach one. Even the agents' own per-run state that Hashi points them at (such as Qwen Code's memory) stays in the token's workspace.
- Agent sandboxes are unchanged in a project: Codex stays read-only, opencode keeps its read-only tools, Gemini CLI and Qwen Code keep their default approval modes, and Claude Code keeps your permission settings.
- Project-level configuration inside the folder may load for agents that read it, such as `.gemini/` for Gemini CLI, Qwen Code's and Cursor's project files. Claude Code stays pinned to your user settings (`--setting-sources user`), and opencode's project config stays off. Crush can run shell code as soon as it loads a project config, so Hashi refuses to run it in a project that contains `.crushrc`, `crushrc`, `.crush.json` or `crush.json`, or sits under a folder that does (see [Crush](#crush)).
- Token holders see only a project's name, in `/v1/me` and on the claim page, never its folder or accounts. A run's error has the folder replaced by `<project>`, though an agent can still mention where it runs in its answer.
- Binding never widens access: a token's agents are intersected with the project's, and a token account list outside the project's is refused, both when binding and when the project is edited.

## Usage limits

To show how much of a plan is left, Hashi reads the quota of Claude Code and Codex sign-ins. Neither read changes a credential.

- **Claude Code.** Hashi reads the account's OAuth access token from where Claude Code keeps it, read only: on macOS the Keychain item `Claude Code-credentials` (with `-` and the first 8 hex characters of the SHA-256 of the NFC-normalised config directory for any account but your default), through `security find-generic-password -a $USER -w -s <service>`, which only prints it; elsewhere, or when there is no Keychain item, `<config dir>/.credentials.json`. It sends the token in one request to `https://api.anthropic.com/api/oauth/usage` with a 5 second timeout and drops it. A token that has expired, or expires within a minute, is not used: the account shows "unknown, refreshes on its next run", because Claude Code renews it itself on its next run.
- **Codex.** Hashi starts `codex app-server` with the account's own `CODEX_HOME` (and the owner's Codex credential variables removed, as for a run), checks that the server reports that same directory, asks `account/rateLimits/read` and stops it. Codex may refresh its own token during that read, so the read is skipped while a run on the same account is going on. The server is contained like a run: it starts in its own process group (a Job Object on Windows) and the whole group is killed when the read ends, times out after 20 seconds or is dropped; each line it prints is capped at 1 MiB, and a longer one ends the read; and it runs in a new, empty, owner-only directory under `~/.hashi/codex-app-server/`, deleted afterwards, rather than the shared temporary directory, where another user could have planted project files.
- **Never refreshed, never kept.** Hashi never refreshes, writes, copies or deletes an OAuth token or the Keychain item. Tokens are not logged, stored in the database, put in `hashi report` or returned by any API. Read errors are redacted before they are logged or stored, and only the used percent, reset time, window name, plan and source are kept.
- **Admins only, unless you share.** Quota figures, plans and reset times are shown only to admin tokens (`GET /v1/accounts`, the refresh endpoint and the dashboard). The OpenAI-compatible API and the claim pages carry none of them. `/v1/me` and the MCP `my_usage` tool (which returns the same document) carry none either, unless you turn on `shareUsage` for that token or invite (see [remote accounts](#remote-accounts)): then both include its `agentUsage` summary, and nothing more. Refreshes are audited and limited to one per account per minute; background reads are at most one per account per minute too, back off on `429` and `403`, and wait an hour after a rejected sign-in.
- **Off switch.** `--no-usage-poll` (or `HASHI_USAGE_POLL=0`) stops the background reads. Figures from runs are still recorded.

## Access requests

Letting people ask for access is off by default: there is no ask-access page until you run `hashi requests open` (or `POST /v1/request-link`), and the link closes by itself after its hours (a week by default, a month at most) or when you close it. Asking never grants anything. Only you accept or decline, from the CLI, the dashboard or the admin API, and there is no rule that accepts on its own.

- **Secrets.** The link code has 128 random bits and the pickup secret a requester gets 256; both are stored only as SHA-256 hashes, and codes travel in request bodies, never in a path or a Referer. Accepting a new person creates a single-use invite whose code is derived from their pickup secret, and the database keeps only its hash, so neither you, the database nor anyone reading it can learn the claim link: only the requester can collect it. An invite nobody collects expires like any other.
- **Abuse limits.** Every submission counts against the rate limit for its client address (`askaccess:<address>`, with the `--rate-limit` budget per minute), and wrong link codes and pickup secrets are throttled per address like invite codes. A link holds at most 50 pending requests and the server 200 from new people; requests for more from token holders have a separate cap of 200, so anonymous requesters filling theirs never stop a token holder from asking. A token holds at most 3 open requests for more and opens at most one an hour. A request nobody decides expires after 7 days, and decided or expired requests are deleted 30 days later by the hourly maintenance.
- **Fields.** The name (1 to 60 characters), message (500), note (200) and decline reason (300) are stripped of control, bidi and zero-width characters before they are stored and checked, and again whenever they are shown, in the API, the CLI, the dashboard and the pages, which use `textContent` only.
- **Privacy.** The ask-access page shows the bridge's name, your note, the project's name and its agents, never other people's requests, folders or account names. Requesters' addresses are not stored with their requests or shown to you.
- **Never wider than you accept.** Accepting fills in what was asked, within the link's project, and your values override it. The same checks as `hashi share` and `token update` apply, so a request cannot take a token outside its project's agents or accounts.

## Remote accounts

A remote account sends prompts to a friend's bridge, with the token they shared with you.

- **Privacy.** The friend who runs that bridge sees every prompt sent through the account and every answer, exactly as you see what the people you share with send. `hashi account add --remote` says so when you add one, as their claim page did. Put a remote account only on tokens and projects whose prompts you are willing to show them.
- **Their token stays private.** It is read from `~/.hashi/remotes.json` (owner only) for each request and sent only in the `Authorization` header, to the address you connected to, with redirects refused. It is never logged, stored in the database, put in `hashi report` or returned by any API; `GET /v1/accounts` and `hashi account list` show only the remote's name.
- **Hidden from the people you share with.** Requests never show token holders which account ran them, and errors from a remote account name no bridge, so they never learn that an account is remote. A run that fails on the friend's bridge shows token holders only "the run failed"; the bridge's own words go to your log and the dashboard. A prompt that fits this Hashi's 64 KB body limit but would not fit the friend's once forwarded is refused here with the usual `413`, rather than sent and refused there.
- **One holder cannot shut the account for everyone.** Only the friend's `limit_reached` (a daily or monthly cap of their token) marks the account limited until its reset. Their `too_many_pending` and `rate_limited`, which one of your token holders can cause with a burst, and an unreachable bridge, back the account off for 5 seconds, doubling on each failure in a row up to 60 seconds, and the next success clears it.
- **Loops.** `GET /v1/status` reports a random instance id kept in this Hashi's database. Adding a remote account whose bridge reports this same id is refused, and every forwarded prompt carries `X-Hashi-From` with it, so a bridge refuses (and the account disables itself on) a prompt it sent itself. Forwarded prompts also carry `X-Hashi-Hops`: a bridge refuses one that has passed through more than 2 bridges and never forwards one that has passed through 2, so a chain of bridges cannot loop forever.
- **Shared usage is opt-in.** A token or invite shows how much quota is left only when you create or update it with `--share-usage` (`shareUsage` in the API). Even then `/v1/me` gives, per agent, the headroom of the best account serving it, its next reset and its state: never account names, how many accounts there are, or the windows. The claim page tells the person when it is on.

## Withdrawing access

Pause holds queued prompts, expiry fails them, and revoke stops running ones at once (within about 2 seconds when you revoke from another terminal with `hashi token revoke`). Revoking deletes the token's workspace, removing symlinks without following them. Every token and invite change is audited. Hashi shuts down cleanly on Ctrl-C, `SIGTERM`, `SIGHUP` and Windows console close, and a second signal exits at once.

## The dashboard

The dashboard draws text that other people wrote: prompts, answers, token and invite names, a bridge's answer. None of it can drive your terminal.

- **No hidden or reordered text.** Every cell and popup title has control characters and Unicode format characters (bidi overrides and isolates, zero-width spaces and joiners, the byte order mark) removed before it is drawn, so a prompt cannot make `exe.txt` read as `txt.exe` or hide part of itself. Token names with bidi or format characters are refused when a token is created or renamed.
- **Safe copies.** Pressing `c` on a bridge's answer copies it with every control character but newline and tab (ESC above all) and every bidi control replaced, so pasting it cannot end a bracketed paste and run what follows.
- **Ctrl-C during a command.** When the dashboard runs an install, a sign-in or an update in the terminal, a Ctrl-C (or another stop signal) that arrives while the command or its "Press Enter" prompt runs belongs to the command and does not stop Hashi afterwards. Outside those windows a signal stops Hashi as before, and a second one exits at once.
- **No stray keys.** Keys typed ahead are dropped before the terminal goes to the command and again when the dashboard takes it back, so keys meant for one never fire in the other.
- **Typed keys.** A key typed into the add-account form is held in one buffer that is wiped when the form closes, and the form is never copied to draw it.

## Network edge

- Hashi binds to `127.0.0.1` by default. Binding elsewhere without TLS prints a warning. Tunnels and HTTPS are opt-in.
- Cross-origin browser access is off unless you list an origin with `--cors-origin`. Over plain HTTP, Hashi answers only requests whose `Host` is an IP address, `localhost`, the `--public-url` host or a name you list with `--allowed-host`, which stops DNS rebinding.
- The claim, ask-access and My access pages load nothing from other sites, run no inline script, and are served with a strict Content Security Policy, `no-referrer` and `no-store`, so an invite code never leaks through a Referer header or a cache.
- Invite links are single-use, hashed, short-lived and create `user` tokens only.

## Data on disk

- On macOS and Linux, `~/.hashi` is created `0700`, and the database with its WAL and SHM files, logs, crash files, the tunnel config and `hashi report` output are `0600`. On Windows, Hashi limits the home to you, SYSTEM and Administrators; a `HASHI_HOME` outside your profile prints a warning, and Hashi refuses to start there if it cannot set that.
- Errors returned to token holders have your home directory replaced by `~` and secrets masked. Headless output strips control and text-direction characters, so agent output cannot rewrite your terminal.
- Every hour Hashi deletes finished requests older than `--retention-days` (never the current month, which monthly caps count from), plus audit records and claimed or expired invites older than the retention period or 90 days, whichever is longer, and access requests decided or expired more than 30 days ago, and the usage windows, usage reads and conversations of accounts that no longer exist, and returns the freed pages to the disk.

## Supply chain

`unsafe` is forbidden in the crate. CI runs `cargo deny` for advisories, licences and sources. Release builds grant write access only to the publish job and pin every action to a commit. The installers verify each archive's SHA-256 checksum and refuse to install when it does not match.

## Known limits

- Spend caps count only finished runs, so prompts already running can take a token past its budget by up to `maxPending` runs.
- Agent runs execute as you, so an agent that can read files can read the account directories and keys under `~/.hashi/accounts`, just as it can read your default login today. Share agents that can read files only with people you would trust with those accounts too.
- Crush can read any file your user can read, even with every write and network tool removed (see [Crush](#crush)). Enable it only for people you would trust with that.
- Codex still loads your global MCP servers; turn one off with `enabled = false` under its `[mcp_servers.<name>]` table in `~/.codex/config.toml`.
- On Windows, npm installs agents such as Codex as `.cmd` shims. Rust refuses to pass arguments it cannot quote safely for a batch file, so a prompt with a line break fails with a clear error, and very long prompts can exceed the 8191-character command line. Hashi stops such shims from picking up a `node` program planted in the workspace.
